# Testing

The full testing guide. [`AGENTS.md`](../../AGENTS.md) carries the rules in brief; read this before writing or changing a test. Italic section names (*Evidence*, *Logging*, *Build, test, lint*) refer to [`AGENTS.md`](../../AGENTS.md).

**Choose a test by where its expected answer comes from, then by how much of the shipped system it runs.** Prefer, in order: **differential, end-to-end, integration** — and add a unit test only when it qualifies below. An expected value written by hand comes from the same reading of the code as the change it checks, and shares that reading's blind spots (see *Evidence*); each step down the list trusts that reading more, runs less of what a user runs, or both.

1. **Differential** — run the same queries or operation history through Spice and through an oracle that shares none of the code under test, and diff the answers: schema and row multiset (ordered rows where an `ORDER BY` fixes the order), never just a count. Oracles already wired up: standalone DuckDB, SQLite and chDB against the accelerators (`crates/cayenne/tests/correctness/`, `crates/runtime/tests/result_correctness.rs`); the federated source against an Arrow acceleration of it, for connector pushdown (`crates/runtime/tests/pushdown_roundtrip/`); unaccelerated clones of the same tables, end to end (`testoperator run bench … --validate`); an in-memory model of a mutation history (`crates/cayenne/tests/mutation_model_test.rs`); and interchangeable implementations of one contract (`crates/cache/src/backend/differential.rs`). A round trip — encode then decode, write then read, unparse then parse, push down then evaluate locally — is a differential test whose oracle is its own input. PostgreSQL and MySQL are oracles too, in a local container (`start_postgres_docker_container` and `start_mysql_docker_container` under `crates/runtime/tests/`) or a CI service container (`postgres_tpch` in `testoperator_run_bench.yml`; `ghcr.io/spiceai/spice-mysql-bench` ships TPC-H and TPC-DS loaded), seeded by `test/tpc-bench/` (`pg-load`, `mysql-load`): send the same SQL straight to the database and diff its answer with Spice's over the same tables, both federated (pushdown and type mapping) and accelerated (refresh, CDC and the accelerator). Run it at the widest scope that can drive it, over a corpus or generated input — TPC-H, TPC-DS, ClickBench, SQLancer-shaped queries, seeded operation histories — not only the cases you thought of. Keep the oracle independent all the way in: rewrite a query for another engine on the parsed statement, never by planning it in DataFusion, or the oracle agrees with Spice on exactly the bugs it is there to catch. Make the query state what engines would otherwise disagree on — NULL placement in every `ORDER BY`, string collation, integer division — so a diff means a bug, not a dialect. Two empty answers agree and have compared nothing, so count them as vacuous, not a pass, and assert that the path under test actually ran (the filter was pushed down, the acceleration was read).
2. **End-to-end (E2E)** — a built `spiced` on a real Spicepod, driven the way a user drives it: SQL over HTTP or Flight, the `spice` CLI, `curl`. `testoperator script` runs the spicescript scenarios in `test/spicescript/` and `testoperator run` runs the Spicepods in `test/spicepods/` (mechanics below); the `e2e_test_*.yml` workflows, with `test/cli/` and `test/models/`, cover the CLI and model flows. Only an end-to-end run exercises what exists only in the shipped binary — the crates and features `spiced` links, wrappers in their real order, Spicepod parsing and defaults, startup and readiness, the wire encodings — and it runs on the one `spiced` build *Build, test, lint* already calls for.
3. **Integration** — the runtime or a crate in-process, with real components rather than a mock of the one under test: `make test-integration` and `crates/runtime/tests/<area>/` (real sources in containers, real accelerators and object stores), and crate suites such as `crates/cayenne/tests/`. Use it where an end-to-end run cannot reach the state deterministically — an injected fault, a forced interleaving, an exact CDC sequence.

**Prefer spicescript for differential and end-to-end tests.** A scenario is both at once: it drives the shipped `spiced` from outside the process and checks rows against an independent oracle (the source itself, another engine, a literal answer, or Spice's own earlier answer). Because it sits outside `spiced`, it reaches what an in-process test cannot:

- **Many configurations from one script**: `matrix:` runs each source or mode separately, `variants:` runs accelerators, refresh modes, and layouts side by side and requires them to give identical answers, and repeated `--spiced` requires several builds to agree.
- **Process lifecycle**: crashes and restarts (`kill-spiced`, `restart`), source outages (`stop-source`, `pause-source`), upgrades in place from a released binary (`--from` with `upgrade` steps), live Spicepod edits, and shutdown.
- **Multiple processes**: several instances over shared state, and a scheduler with executors (`--cluster`, `kill-executor`).
- **Plan and observability properties**: `explain` (and corpus `-- plan-has`/`-- plan-lacks`/`-- sends`) requires plan fragments — the join kind chosen, a filter pushed to the source, an index used — while `wait-metric`, `assert-log`, and `assert-status` check metrics, log lines, and dataset status.

It meets the bar below by construction: rows compare as a multiset, two empty answers fail unless the script says empty is the point, generated data is seeded, and waits poll (`eventually`, `wait-metric`). Changing a scenario is a YAML edit with no rebuild. **Extend an existing script before writing a new one**: add the query, step, variant, or matrix value to the script that already covers that area, so its setup is shared and the suite does not grow a near-copy; write a new script only for a scenario no existing one fits. Use an integration test only for what a script cannot drive (state inside the process), and `testoperator` for benchmarks and performance numbers.

**Every test, at every tier, meets this bar:**

- **Watched failing.** Before a test lands, break the behavior it guards — revert the fix, delete the branch, invert the comparison — and show it go red, then green on the real code. A test you have never seen fail proves nothing, and one that cannot fail is not a test. For a bug fix this is *Evidence*'s before and after.
- **Exact outcomes.** Assert the exact rows, value, error variant or message, plan node, or metric value — never only `is_ok()`, `is_err()`, `is_some()`, a non-empty result, a non-zero count, or that nothing panicked — and give `#[should_panic]` its `expected` message. Floating-point and computed decimal values may compare within a stated tolerance, and only where engines legitimately differ in the last digits: `--validate` accepts a 0.1% relative difference (`NUMERIC_RELATIVE_TOLERANCE` in `crates/test-framework/src/queries/validation/mod.rs`). Everything else compares exactly. An assertion that a different wrong answer would also pass is not checking the answer.
- **Non-vacuous.** Assert that the path under test ran — the filter was pushed down, the acceleration was read, the cache was hit, the retry fired — so the test fails when the feature is off instead of passing on the fallback.
- **Deterministic.** Seed every random input and print the seed on failure, poll conditions instead of sleeping (mechanics below), and depend on wall-clock time, test order, or the network only when that is what is under test.

**Unit tests only when they earn it** — add one only when it is at least one of:

- **Critical**: it guards an invariant whose break returns wrong results or loses data — NULL semantics, overflow and boundaries, type coercion, encode/decode round trips, delete and merge logic — where a guard that runs on every `make test` and sign-off is worth having beside the higher-tier test.
- **High-value**: it pins behavior no higher tier reaches cheaply or deterministically — an error branch, an exact batch or page boundary, a seeded randomized or exhaustive sweep over a pure function's inputs.
- **Data- or snapshot-verifiable**: it asserts concrete output a reviewer can check by reading it — rows, encoded bytes, a plan, a user-facing message (see *Logging*) — exactly or against a named insta snapshot, never a mock, a call count, or an internal flag.

Skip the unit test that restates the implementation (a getter returns what the setter stored), asserts that a mock was called, or repeats what a differential, end-to-end, or integration test already covers. An existing unit test that falls short is strengthened, or deleted once a higher-tier test covers what it meant to check — never deleted blind. A green unit test is still not proof that a bug existed or is gone (see *Evidence*).

**Always keep performance, round-trip, and benchmark tests.** Benchmarks (`crates/*/benches/`, `make test-bench`, `testoperator run bench|throughput|load|htap`), round-trip tests, and performance tests are the evidence every other rule here relies on, so they are never pruned: one that falls short of the bar is strengthened, not deleted.

**Performance is always tested.** Every change to code that ships in `spiced` or `spice` carries before and after numbers for the paths it touches, from the same rig, with each arm's commit recorded: a Criterion bench (`cargo bench -p <crate> --bench <name>`) for a kernel or a hot function, `testoperator run bench` or `throughput` for a query, acceleration, or refresh path, `testoperator run htap` for CDC lag and freshness. "No performance impact" is a claim like any other and needs the numbers. Report the tail — P99, or P99.9 where the run has the samples — never a mean or a P50 (testoperator records `p99_duration_ms` per query). Interleave the arms (A, B, B, A, …) over enough repetitions to show the noise floor, and call a delta inside it no change. A regression on any query or at any scale factor blocks the change, and a win elsewhere does not offset it: split the change until the regressing part is isolated. A change that cannot reach a shipped binary — docs, CI, tests — says so in place of the numbers.

## Mechanics

- **Spicepod naming**: `{connector[variant]}-{accelerator[variant]}-{test_variant}`; non-accelerated must use the `-federated` suffix. Examples: `s3[parquet]-federated`, `mysql-duckdb[file]-on_zero_results`.
- **testoperator** is the benchmark/test harness: `cargo run -p testoperator -- run bench -p test/spicepods/tpch/sf1/federated/duckdb.yaml -s spiced -d ./.data --query-set tpch --validate` (also `run throughput … --concurrency 25`). `--validate` compares each answer with an oracle: the spec answer files for TPC-H at scale factor 1; the same SQL over unaccelerated `__test_reference.*` clones of the tables for TPC-DS, ClickBench, and TPC-H at other scale factors; a scenario's own expected rows. `tools/testoperator/README.md` lists the Spicepods that have no oracle.
- **spicescript** scenarios (`test/spicescript/*.yaml`) run through `testoperator script` against a prebuilt `spiced` (Docker required): `cargo build -p testoperator && target/debug/testoperator script --spiced dev=target/release/spiced test/spicescript/<script>.yaml` (`--jobs N` for parallel instances, `--check` to parse only, `--matrix`/`--variant` to narrow a run). The merge queue (`test_spicescript` in `e2e_test_ci.yml`) runs every script not tagged `tags: [long]`, plus any `long` or known-failing script the PR adds or changes (an edit only to its `tags:` or `duration:` lines does not count); `trunk_tests.yml` runs every script after merge, on trunk, and `known-failing/` against its recorded failures. So every new or changed script runs before merge: a `long` one in the changed-scripts job, the rest in the routine shards. `--exclude-tag long` gives a quick local run. A new script commits its recorded run time, its `duration:` line (`--record-durations`). Authoring, steps, oracles, and the expected-failures ledger: [`tools/spicescript/README.md`](../../tools/spicescript/README.md); suite layout: [`test/spicescript/README.md`](../../test/spicescript/README.md).
- **One integration test binary per crate**: `autotests = false`, a single `[[test]] name = "integration"`, and one `mod` per test file in `tests/integration.rs` (gate a module with `#[cfg(feature = …)]`, not `required-features`). Every extra binary relinks the crate's whole dependency graph — folding cayenne's 104 cut a post-edit rebuild ~7.7x and its test executables from 69 GB to 3 GB. A test that changes process-global state stays in `integration`, runs under nextest (process per test), and calls the crate's `require_process_per_test(why)` first; that state is never a reason for a separate binary. A separate `[[test]]` is only for a `#[global_allocator]`, a custom `main`, libraries that cannot share one process, a test the macOS sign-off gate must load without runtime's `integration`, or a CI step of its own, and its `Cargo.toml` comment names which. `make lint-rust` fails on a test file no target compiles. See `docs/dev/integration_test_layout.md`.
- **No fixed sleeps as readiness waits**: poll the actual condition with a bounded timeout, short interval, and a failure message carrying the last observed state — `runtime_ready_check[_with_timeout]`, `wait_until_true`, `util::retry` with `FibonacciBackoffBuilder`, health/ping probes, `SELECT 1`, refresh notifiers, result polling. Fixed sleeps only when time itself is under test (TTL, backoff, cron, rate limits) — keep them short and explain them.
- **Insta snapshots**: always named `.snap` files — `insta::assert_snapshot!("name", value)` — never inline `@r"…"` (bloats sources, diffs poorly). Regenerate with `INSTA_UPDATE=1 cargo test` and review; never hand-edit `.snap` files.
- **Debugging integration tests**: the runtime test harness uses a thread-local tracing subscriber, so logs from worker threads (e.g. dataset loads) are dropped — use `eprintln!` for debug output, not `tracing`.
