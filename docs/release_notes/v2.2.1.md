# Spice v2.2.1 (September 1, 2026)

Spice v2.2.1 is a patch release focused on the correctness and the disk footprint of accelerated data. Cayenne accelerations now reclaim the space that maintenance leaves behind instead of growing without bound, several paths that could return a wrong or missing row are fixed, and a new suite of metrics makes Cayenne's maintenance decisions and storage growth visible without re-running a workload under debug logging.

Highlights in v2.2.1 include:

- **[Cayenne reclaims its disk and metastore space](#cayenne-reclaims-its-disk-and-metastore-space)** — six reclamation gaps that let a steadily-written table grow without bound are closed
- **[Correct results on more query paths](#correct-results-on-more-query-paths)** — negative JSON numbers, `Date64` file pruning, DuckDB search filters, and an upsert-table `DELETE` no longer return the wrong rows
- **[Cayenne maintenance and footprint metrics](#cayenne-maintenance-and-footprint-metrics)** — new metrics answer whether each maintenance pass ran, why it declined, and where the disk went
- **[Bounded memory for DuckDB and HTTP accelerations](#bounded-memory-for-duckdb-and-http-datasets)** — the bundled DuckDB is back on v1.4.4, and the HTTP connector's response cache is now bounded and honours `no-store`

## What's New in v2.2.1

### Cayenne Reclaims Its Disk and Metastore Space

A Cayenne acceleration under steady writes could grow on disk indefinitely, because several kinds of superseded state were made unreachable but never removed. Each gap is now closed, and no configuration change is required:

- **Inline tombstones are reclaimed.** An upsert writes a tombstone per superseded primary key. On a workload whose rows never land inline, nothing removed them — they accounted for 86–99% of metastore growth in measured runs, reaching 240 MB in an hour. The tombstone table is now budgeted in bytes alongside the inline row corpus, and the checkpoint that clears it can be reached whatever the corpus holds.
- **Superseded snapshot directories are reclaimed against live state.** Cleanup swept against the snapshot id captured when it was queued rather than the current one, so it behaved as a sliding two-minute window rather than a drain: a dataset refreshing every 200 ms held 323 dead directories and 223 MiB against a 0.69 MiB live table.
- **Manifest and statistics rows are deleted with the snapshot they describe.** Protected-snapshot compaction, subset small-file compaction, and retention cleanup each removed a snapshot from the live set while leaving its `cayenne_snapshot_file` and `cayenne_snapshot_file_statistics` rows in the metastore.
- **Orphaned deletion vectors are swept from every publication that orphans one.** Only file-based retention signalled the sweep, so a workload that compacts but never empties a snapshot leaked one deletion-vector file and one metastore row per refresh, forever. Sequence-prefix bakes and protected-snapshot merges now signal too, and a signal raised while a sweep is running is no longer discarded.

`retention_sql` predicates that call `now()` — for example `DELETE FROM t WHERE arrival_time < now() - INTERVAL '7 days'` — now work. The predicate is resolved once per maintenance pass, so a default configuration evicts expired rows instead of failing the pass silently and re-arming.

### Correct Results on More Query Paths

- **A predicate `DELETE` on a Cayenne upsert table no longer destroys rows the predicate does not match.** The deletion sink matched the predicate against files rather than against the visible row set, so it could tombstone a primary key from a superseded row version and hide the live one with it. Reproduced end to end: a key upserted to `60`, then `DELETE FROM t WHERE value < 50`, left the table empty. Only an upsert table and a non-primary-key predicate were needed to hit it.
- **`json_get_int` and `json_get_float` read negative numbers.** `json_get_int('{"a": -1}', 'a')` returned NULL, not `-1`, on every shipped version — no error, no warning. The same fix picks up a panic on large integers and a wrong value read out of a JSON string that itself holds JSON. JSON extraction functions can also now be pushed down to BigQuery.
- **`Date64` columns prune correctly in Vortex files.** A pushed-down `CAST(date_col AS TIMESTAMP)` failed the scan outright for `Date32`, and for `Date64` silently compared a millisecond count as a nanosecond one when deciding whether to read a file.
- **DuckDB search filters are rendered against the table schema.** A pushed-down filter on a timezone-aware timestamp column was rewritten through `EPOCH_MS`, truncating it to whole milliseconds. Because the pushdown promises exactness, DataFusion dropped the filter rather than re-checking, so a search returned a different set of rows than the caller asked for.
- **Spice-only UDFs no longer federate to ADBC sources.** Since v2.2.0, functions such as `json_get_str` were pushed into the SQL sent to ADBC sources (for example BigQuery) and failed as unknown functions; `query_federation: disabled` was validated and then ignored. Both are restored.
- **A duplicate row for a declared primary key is no longer possible after a failed index rebuild.** Cayenne's primary-key existence index is taken out of its cache under a checkout window; an error on the rebuild path left the window open, which disabled the pending-key log for the rest of the process and let an in-flight validation admit a key another writer had already committed. Every exit path now closes the window.
- **A distributed `COUNT(*)` no longer answers from a short count.** A commit published its rows before claiming the matching row-count delta, so a reader landing between the two was served the pre-write count as a provably exact one.
- **Point lookups plan again on Cayenne CDC datasets.** `SELECT ... WHERE pk = ? ORDER BY pk` stopped planning from the first transactional commit onward because the scan's constant columns were dropped across the schema cast. It failed closed — the query was rejected, never answered wrongly.

### Cayenne Maintenance and Footprint Metrics

Cayenne's maintenance passes mostly decide *not* to run, and each correct decline leaves the table slightly larger. Those declines were `tracing::debug!` lines and nothing countable, so "nothing is reclaiming" could not be told apart from "reclamation ran and found nothing."

This release adds a large set of metrics on the existing `cayenne` meter, served at `/metrics` when `spiced` is started with `--metrics <addr>`. They cover whether each pass ran and why it declined (`cayenne_compaction_outcome_total`, `cayenne_maintenance_outcome_total`), how much it gave back (`cayenne_maintenance_reclaimed_{files,bytes,rows}_total`), where the disk is going (`cayenne_storage_*`, `cayenne_data_dir_*`, `cayenne_metastore_*`), where the RAM is going, and whether the primary-key index is healthy. The full reference, including the label vocabulary, is in Appendix C of the Cayenne technical reference.

### Bounded Memory for DuckDB and HTTP Datasets

**The bundled DuckDB is back on v1.4.4.** On v1.5.5 the write path an accelerated dataset uses — an `ON CONFLICT ... DO UPDATE` upsert per refresh — grew memory without bound at a steady row count, about 6 MiB per cycle, until the write failed with an out-of-memory error.

**Concurrent queries survive a file-mode DuckDB swap.** Two or more file-mode DuckDB accelerations on separate `duckdb_file`s cross-`ATTACH` each other, and every pooled connection is a clone of one DuckDB instance, so replacing one file made concurrent queries against the others fail. Measured over 12 replacements with 8 concurrent clients per dataset, HTTP 400s went from 19 and 16 to zero.

**The HTTP connector's response cache is bounded.** It kept every fetched response in a map that was never pruned, and the keys are request-shaped, so on an API-proxy workload the memory was unbounded by construction and invisible to `runtime.caching` limits and to metrics. It is now bounded in bytes with per-entry expiry, reports per-dataset metrics, and honours `no-store` and `no-cache` at admission rather than caching in defiance of them.

### PostgreSQL Write-Back No Longer Echoes Into Its Own Acceleration

When a CDC-accelerated dataset writes back to its PostgreSQL source, the logical-replication stream echoes that write back to the accelerator, which can double-apply the data. Spice now records the transaction id of each write-back transaction it issues in a per-dataset registry and drops the matching transaction's changes from the CDC stream. Entries are pruned only once the acked position has passed them, so a slot reconnect that replays the echo still drops it.

Durable write-back also now works for a table whose primary key is a single `BIGINT` column. Such a table selects a converter-free deletion strategy, and the write-back marker decoder was the one path that assumed the converter cache was populated, so committed values were never delivered to the source. Transactional writes exposed this reliably, since the durable delivery worker is their only path to the source.

### Other Fixes

- **MySQL accelerations rebuild from a purged binlog position** when `mysql_replication_invalid_checkpoint_behavior: restart` is set, even alongside `mysql_replication_initial_snapshot: disabled`. Previously a durable acceleration silently resumed from the current head, leaving rows deleted inside the unreachable window in the acceleration forever.
- **Append refresh resumes correctly on Vortex and Cayenne.** The watermark read cast the time column on the sort key, which pushed a filter Vortex has no kernel for into the scan; the read errored, the high-water mark never advanced, and the dataset stopped appending.
- **Startup log events reach the configured subscriber.** `Runtime::build()` ran with no subscriber, so everything it emitted was dropped at every level — the DuckDB accelerator memory budget and its recommended limits, the query memory-limit defaults, the invalid `runtime.query.timeout` warning, and secret-store load failures.
- **`spice login` reconciles credential state.** Stale copies in the unselected store are cleared, a shell variable that still overrides the newly stored login is named in the error, the active organization is reconciled before login reports success, and Cloud Connect now reports an expired, revoked, or wrong-account credential differently from a missing login.
- **A pinned single write partition means one writer.** A configured `cayenne_write_concurrency` overrode a caller that passes `target_partitions = 1` specifically to require a serial write — the position-delete subset merge and the sorted rewrites.
- **Embedding models pad correctly.** The runtime kept the padding and truncation declared in `tokenizer.json`, so a `sentence-transformers` model declaring a fixed 128-token padding length had its padding tokens carried into self-attention and the mean-pool step, letting them dominate the pooled vector for short inputs.
- **Cayenne accelerations can store Arrow `Map` columns in `mode: file`.** Every flush of an HTTP dataset carrying `response_headers` failed with a warning while `/health` stayed `ok` and queries returned no error, so the accelerator was permanently empty and every signal pointed the wrong way. `Union` and `RunEndEncoded` columns — which also could never be stored — are now refused when the table is created, naming the column, and a caching accelerator that stores none of its writes reports the dataset unhealthy.

## Breaking Changes

No breaking changes.

Two behavior changes are worth noting before upgrading:

- **The bundled DuckDB is downgraded from v1.5.5 to v1.4.4** to fix unbounded memory growth on the accelerated write path. SQL features introduced in DuckDB v1.5.x are no longer available to DuckDB-accelerated datasets.
- **The HTTP data connector now honours `no-store` and `no-cache`.** A response that sends either is no longer retained, even when it also sends a `max-age`. A response that sends no `Cache-Control` at all remains uncached by default.

## Upgrading

To upgrade to v2.2.1, use one of the following methods:

**CLI**:

```console
spice upgrade
```

**Homebrew**:

```console
brew upgrade spiceai/spiceai/spice
```

**Docker**:

Pull the `spiceai/spiceai:2.2.1` image:

```console
docker pull spiceai/spiceai:2.2.1
```

For available tags, see [DockerHub](https://hub.docker.com/r/spiceai/spiceai/tags).

**Helm**:

```console
helm repo update
helm upgrade spiceai spiceai/spiceai --version 2.2.1
```

**AWS Marketplace**:

Spice is available in the [AWS Marketplace](https://aws.amazon.com/marketplace/pp/prodview-jmf6jskjvnq7i).
