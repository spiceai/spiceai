# Spice v2.4.2 (November 6, 2026)

Spice v2.4.2 is a patch release that adds short-lived credentials, fixes Snowflake key-pair authentication, and continues security hardening. OpenAI, Anthropic, Azure OpenAI, and Databricks can now authenticate with workload identity federation, as AWS connectors and Bedrock already do. GitHub datasets can sign with a GitHub App key in Azure Key Vault or AWS KMS. Snowflake datasets with key-pair authentication load again after they failed in the v2.4.0 and v2.4.1 release binaries. Security fixes limit the nesting depth, the expanded size, and the memory use of SQL queries, and HTTP datasets refuse redirects to other internal hosts. The release also fixes SQL, Spice Cayenne, and runtime issues, such as wrong results for `a IS DISTINCT FROM b OR c`.

All users of v2.4.x should upgrade, but first read [Breaking Changes](#breaking-changes) for the new query limits.

Highlights in v2.4.2 include:

- **Workload identity for OpenAI, Anthropic, Azure OpenAI, and Databricks.** The runtime exchanges the identity of the workload for short-lived tokens, with no stored API key.
- **GitHub App keys in Azure Key Vault and AWS KMS.** The runtime signs the GitHub App JWT with the key service and never reads the private key.
- **Snowflake key-pair authentication works again.** Datasets no longer stop at `Initializing` with a `jsonwebtoken` panic.
- **Security hardening.** The runtime checks the depth and size of each SQL query before it plans it. More SQL functions now count their output against the query memory limit. HTTP datasets refuse redirects to other internal hosts, and API responses no longer show URL credentials.

## What's New in v2.4.2

### Workload Identity for OpenAI, Anthropic, Azure OpenAI, and Databricks

[OpenAI](https://spiceai.org/docs/components/models/openai), [Anthropic](https://spiceai.org/docs/components/models/anthropic), and [Azure OpenAI](https://spiceai.org/docs/components/models/azure) models, and [Databricks](https://spiceai.org/docs/components/data-connectors/databricks) datasets and models, can now authenticate with workload identity federation, with no API key. The runtime exchanges the identity token of the workload for a short-lived access token from the provider. It exchanges the token again before it expires. This applies to chat, responses, and embeddings.

```yaml
models:
  - from: openai:gpt-4o-mini
    name: gpt
    params:
      openai_identity_provider_id: ${ secrets:OPENAI_IDENTITY_PROVIDER_ID }
      openai_service_account_id: ${ secrets:OPENAI_SERVICE_ACCOUNT_ID }
      openai_identity_token_audience: https://api.openai.com
      # openai_identity_token_file: /var/run/secrets/tokens/openai
  - from: anthropic:claude-haiku-4-5
    name: claude
    params:
      anthropic_federation_rule_id: ${ secrets:ANTHROPIC_FEDERATION_RULE_ID }
      anthropic_organization_id: ${ secrets:ANTHROPIC_ORGANIZATION_ID }
      anthropic_service_account_id: ${ secrets:ANTHROPIC_SERVICE_ACCOUNT_ID }
      anthropic_workspace_id: ${ secrets:ANTHROPIC_WORKSPACE_ID }
```

The runtime reads the identity token from `openai_identity_token_file` or `anthropic_identity_token_file`. When neither setting is present, the runtime requests the token from the GitHub Actions job. Outside of GitHub Actions, set the token file.

Azure OpenAI models use Microsoft Entra workload identity with the settings `azure_tenant_id`, `azure_client_id`, and `azure_federated_token_file`. When the model has no `azure_api_key` or `azure_entra_token`, these settings default to `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, and `AZURE_FEDERATED_TOKEN_FILE`. On AKS, a model needs only its `endpoint`.

Databricks datasets, catalogs, models, and embeddings authenticate as a service principal. Set `databricks_client_id` with `databricks_token_audience` on GitHub Actions, or with `databricks_oidc_token_filepath` elsewhere. `databricks_client_id` alone still selects U2M authentication. Existing `databricks_token`, M2M, and U2M setups do not change.

AWS connectors and Bedrock models already get short-lived credentials from the AWS credential chain, for example with IRSA or EKS Pod Identity. They do not change in this release.

A component with both an API key and workload identity settings in the Spicepod fails with a configuration error that names the setting to remove.

### GitHub App Private Keys in Azure Key Vault and AWS KMS

[GitHub](https://spiceai.org/docs/components/data-connectors/github) datasets can now sign the GitHub App JWT with a key in Azure Key Vault or AWS KMS. The runtime never reads the private key. Set `github_private_key_kms` to the key URL or the key ARN:

```yaml
datasets:
  - from: github:github.com/acme/widgets/issues
    name: issues
    params:
      github_client_id: Iv23liAbCdEf
      github_installation_id: '12345678'
      github_private_key_kms: https://acme-vault.vault.azure.net/keys/github-app # or arn:aws:kms:us-east-1:111122223333:alias/github-app
```

The runtime reaches the key service with the cloud identity of the workload. A dataset that sets `github_private_key_kms` together with `github_private_key` or `github_token` fails with a configuration error.

This release also fixes GitHub App authentication on GitHub Enterprise Server. The runtime now requests the installation token from `github_endpoint`. Before this release, it always used `https://api.github.com`. A failed token refresh is now a warning that names the dataset.

### Snowflake Key-Pair Authentication Works Again

[Snowflake](https://spiceai.org/docs/components/data-connectors/snowflake) datasets with key-pair authentication load again. In the v2.4.0 and v2.4.1 release binaries, the dataset stopped at `Initializing` with this panic:

```text
Could not automatically determine the process-level CryptoProvider from jsonwebtoken crate features.
```

The release build enabled two crypto backends of the `jsonwebtoken` crate, and `jsonwebtoken` 10 refuses to select one. The runtime now installs the aws-lc backend at startup, for every JWT signer in the process. v2.3.x did not have this fault.

### SQL Query Limits Protect the Runtime

Spice now limits the nesting depth, the expanded size, and the memory use of SQL queries. A query over a limit fails with HTTP 400 on `/v1/sql`, or with `InvalidArgument` on Flight SQL. The runtime continues to serve other queries. Before this release, any client that could send SQL could stop the runtime with one query. A deeply nested query overflowed the stack, and the process stopped with `fatal runtime error: stack overflow, aborting`. Other queries made one function or one plan allocate memory without a limit.

The checks apply to HTTP `/v1/sql`, `/v1/nsql`, Flight SQL statements and prepared statements, Flight SQL updates, and transactions. Each limit is in [Breaking Changes](#breaking-changes). The checks cover these shapes:

- **Long expressions.** A chain of `+`, `||`, `AND`, or `OR` terms deeper than 512 levels fails. This includes a `/v1/search` `where` condition.
- **Nested queries.** Subqueries, or common table expressions (CTEs) that each read the CTE before them, fail past 64 levels.
- **CTE expansion.** A query fails when its CTE references expand to more than 4096 table references. The planner makes a copy of the plan of a CTE for each reference to it.
- **Nested data types.** A data type such as `ARRAY<ARRAY<…>>` fails past 32 levels. A type such as `INT[][]…` fails past 64 levels.
- **Arrow type strings.** An Arrow type string, such as an `arrow_cast` argument or a column type that a dataset declares, fails past 64 levels.
- **Grouping sets.** A `GROUP BY` that expands to more than 4096 grouping sets fails. `CUBE` of 13 expressions makes 8192 sets. 4096 is also the limit in PostgreSQL.
- **Search keywords.** A `/v1/search` request with more than 512 `keywords` fails with HTTP 400.

These scalar functions now keep their output within `runtime.query.memory_limit`, or within a fixed cap:

- **`lpad` and `rpad`** charge the whole output buffer to the memory limit. This includes an empty fill string and negative lengths. A query that does not fit fails with `Resources exhausted`.
- **`array_repeat` and `list_repeat`** charge the real size of a list, struct, binary, boolean, or `NULL` element. Before this release, they charged 1 byte for each copy of such an element.
- **`flatten_json_properties`, `json_tree`, and `flatten_json`** stop at 32 × `max_bytes` of output for one document. `max_depth` is limited to 128. A small JSON schema with repeated `allOf` or `$ref` entries no longer expands exponentially.
- **`truncate`** cuts text by characters, not bytes. Non-ASCII text made the query fail with `Query driver task ended unexpectedly`.

Flight SQL metadata requests also have limits. `GetSqlInfo` info IDs and `GetTables` table types are limited to 1024 entries. `GetTables` and `GetDbSchemas` filter patterns are limited to 1024 bytes.

### Credentials Stay out of API Responses and Logs

`GET /v1/datasets` and `GET /v1/catalogs` no longer return credentials from the `from` value of a component. Before this release, any API key that could list components could read a password in a source URL, such as `https://user:password@host/file.csv`. This included a read-only key. The runtime now removes `user:password@` from each URL. It replaces values of query keys such as `password`, `secret`, `token`, and `sig` with `***`. With `status=true`, `/v1/datasets` also removes credentials from `error_message`. Sources with no credentials do not change.

The runtime also removes credentials from these errors and log lines:

- **[ADBC](https://spiceai.org/docs/components/data-connectors/adbc) connection errors.** Setup errors no longer contain `adbc_uri`. The runtime replaces each configured secret in the driver message with `***`. Before this release, the full URI went to the warning log and to `/v1/datasets?status=true`.
- **MCP transport errors.** The error no longer contains the URL of the MCP server. A URL can contain a credential.
- **`.env` files.** The warning for a malformed line gives only the line number, not the line content.

### HTTP Datasets Refuse Redirects to Other Internal Hosts

An [`http` or `https`](https://spiceai.org/docs/components/data-connectors/https) dataset in a file format, such as CSV or Parquet, no longer follows a redirect to an internal host. An internal host is a different host that is a loopback, private, or link-local address, or that resolves to one. The dataset fails with this error:

```text
Refused to connect to <target>: the HTTPS data connector does not follow a redirect to a private, loopback, or link-local address
```

The host of the dataset itself is always allowed, also when it is internal. Redirects that stay on that host still work. `SPICE_URL_TABLE_ALLOW_PRIVATE_HOSTS=true` turns off the check.

### `IS [NOT] DISTINCT FROM` Before `AND` or `OR` Returns Correct Results

Queries with `a IS [NOT] DISTINCT FROM b AND c` or `a IS [NOT] DISTINCT FROM b OR c` no longer return wrong results. The SQL parser read `b AND c` or `b OR c` as the right operand of `IS [NOT] DISTINCT FROM`. This applies to every dataset and to every query path.

- With boolean operands, the query returned wrong values with no error. For example, `SELECT true IS DISTINCT FROM true OR true` returned `false`. A `WHERE` filter of this form dropped rows.
- With other operands, the query failed to plan with `Cannot infer common argument type for logical boolean operation Int64 OR Boolean`.

The parser now gives `IS [NOT] DISTINCT FROM` a higher precedence than `AND` and `OR`, as PostgreSQL does. Conditions that use parentheses, such as `(a IS DISTINCT FROM b) OR c`, returned correct results before this release and do not change.

The fault is in sqlparser 0.62.0, which DataFusion 55 uses. The upstream fix, apache/datafusion-sqlparser-rs#2436, is in sqlparser 0.63.0. Spice applies that fix to a vendored copy of sqlparser 0.62.0 until it upgrades to DataFusion 56.

### Spice Cayenne Checks File-Mode Data Files at Startup

A [Spice Cayenne](https://spiceai.org/docs/components/data-accelerators/cayenne) file-mode acceleration that lost data files between restarts no longer serves incomplete results. Before this release, the dataset reported `Ready`, and queries returned the rows of the remaining files, or no rows. The runtime logged no warning or error.

At startup, Cayenne now compares the data files that its metastore records with the files on disk. It checks that each file exists and has the recorded size. It does not read the files. When the files do not match, the result depends on the dataset:

- **Spice can reload the dataset from the source**, for example with `refresh_mode: full`. Cayenne logs a warning that names the files, then drops the acceleration and reloads it. If the runtime cannot read the source yet, the dataset is in `Error` until it can.
- **Spice cannot reload the dataset**, for example with `refresh_mode: append`, `refresh_mode: changes`, or writes to the acceleration. If a snapshot directory does not exist, or a file has a different size, the dataset fails to load. The error says how to reload it.
- **Spice cannot reload the dataset, and files are only missing.** Cayenne logs a warning that names the files and continues to serve the dataset.

The check does not apply to S3-backed tables, to memory mode, or to tables written before Cayenne recorded its data files. File-based retention now also removes the record of each file that it deletes.

### Other Bug Fixes

- **`COUNT(DISTINCT …)` on list or struct columns.** A query with two or more `COUNT(DISTINCT …)` aggregates no longer fails with `Resources exhausted` when one of them reads a list or struct column. Before this release, the query failed at about 50,000 rows and requested tens of GB. Each stored value held a reference to its whole input batch. This applied to federated and Cayenne queries, with or without `GROUP BY`.
- **Databricks models and embeddings.** Chat and embedding calls to [Databricks](https://spiceai.org/docs/components/models/databricks) models no longer fail with HTTP 404. Before this release, the runtime sent the request with an empty path, with every authentication mode. The runtime now calls `/serving-endpoints/{model}/invocations`.
- **Queries after a burst of stale cache hits.** With `stale_while_revalidate_ttl` set on the [SQL results cache](https://spiceai.org/docs/features/caching), new client queries no longer wait behind background revalidations. In a test, 600 stale hits made the next uncached query wait 321.8 seconds, and 6.3 seconds with this fix. At most one quarter of the query admission limit runs revalidations at the same time. A stale hit over that limit gets the cached result with no revalidation, and `results_cache_stale_swr_count` counts it. The runtime cancels a revalidation after 5 minutes and records the outcome `timed_out`.
- **`truncate` on numbers.** `truncate` no longer returns wrong values for integers and decimals near the limits of their type. For example, `truncate(100, arrow_cast(50, 'Int8'))` returned `56`, and the correct result is `0`. A result that does not fit its type is now an error.
- **SQL scalar functions with no arguments.** A `from: sql` scalar function with no arguments no longer fails on every call.
- **Certificate errors in the CLI.** `spice` HTTP commands, such as `status` and `refresh`, report a TLS certificate failure as a TLS error. In v2.4.1, the release build reported it as `The Spice runtime is unavailable`.
- **AWS session tokens.** The runtime no longer sends an empty AWS session token together with static keys. A secret that is not set gives an empty token. This applies to S3, Delta Lake, and AWS SDK connectors.

### Dependency Updates

- `arrow-rs` (Spice fork): 59.3.0 → 59.3.2. This update fixes RUSTSEC-2026-0442 in run-end-encoded array validation, and it adds the 64-level limit for Arrow type strings.
- `azure_security_keyvault_secrets`: 0.10.0 → 1.0.1. This update fixes RUSTSEC-2026-0438 in the Azure Key Vault secret store. `azure_identity` and `azure_core` move to the 1.x line for that store.
- `sqlparser`: 0.62.0, vendored with the precedence fix from apache/datafusion-sqlparser-rs#2436.
- DataFusion (Spice fork): the pin adds the fixes for `COUNT(DISTINCT …)` memory and for nested SQL data types.

DataFusion remains at v55.2.0, and Arrow moves to v59.3.2.

## Breaking Changes

**Query limits.** These queries now fail with HTTP 400 or Flight `InvalidArgument`. Before this release, some of them stopped the runtime.

| Shape | Limit |
| --- | --- |
| Expression depth, such as a chain of `AND`, `OR`, `+`, or `\|\|` | 512 levels |
| Query nesting: subqueries, or CTEs that read each other | 64 levels |
| Table references after CTE expansion | 4096 |
| SQL data type nesting with `ARRAY`, `STRUCT`, `MAP`, and similar keywords | 32 levels |
| SQL data type nesting with `[]` | 64 levels |
| Arrow type string nesting | 64 levels |
| `GROUP BY` grouping sets | 4096 (`CUBE` of up to 12 expressions) |
| `/v1/search` `keywords` | 512 |
| Flight SQL `GetSqlInfo` info IDs and `GetTables` table types | 1024 entries |
| Flight SQL `GetTables` and `GetDbSchemas` filter patterns | 1024 bytes |

CTEs that do not read each other are not limited by depth. Table references outside of CTEs do not count toward the expansion limit.

**Scalar functions.** `truncate` returns an error, not a wrapped value, when the result does not fit its type. `lpad`, `rpad`, `array_repeat`, and `list_repeat` fail with `Resources exhausted` when their output does not fit `runtime.query.memory_limit`. JSON flattening of a very large or deeply nested document stops at the new output cap.

**HTTP dataset redirects.** An `http` or `https` dataset in a file format fails when its server redirects to a different internal host. To allow it, set `SPICE_URL_TABLE_ALLOW_PRIVATE_HOSTS=true`.

**Spice Cayenne file mode.** At startup, a file-mode acceleration with missing or changed data files reloads from the source, or fails to load. See [Spice Cayenne Checks File-Mode Data Files at Startup](#spice-cayenne-checks-file-mode-data-files-at-startup).

## Upgrading

To upgrade to v2.4.2, use one of the following methods:

**CLI**:

```console
spice upgrade
```

**Homebrew**:

```console
brew upgrade spiceai/spiceai/spice
```

**Docker**:

Pull the `spiceai/spiceai:2.4.2` image:

```console
docker pull spiceai/spiceai:2.4.2
```

For available tags, see [DockerHub](https://hub.docker.com/r/spiceai/spiceai/tags).

**Helm**:

```console
helm repo update
helm upgrade spiceai spiceai/spiceai --version 2.4.2
```

**AWS Marketplace**:

Spice is available in the [AWS Marketplace](https://aws.amazon.com/marketplace/pp/prodview-jmf6jskjvnq7i).
