# Spice v2.4.0 (October 27, 2026)

Spice v2.4.0 expands data ingestion, caching, and AI decisions. Spice Cayenne is now the default data accelerator, with persistent secondary indexes and automatic primary-key handling. Spice's AI runtime now supports OpenAI-compatible `/v1/decisions` API, TypeSafe models and 5 new decision UDTFs in SQL. S3 datasets can ingest new objects through SQS, and snapshots can serve read-only datasets without the original source. This release also adds SQL results-cache warmup, Hugging Face datasets, ORC files, and Iceberg reads without a catalog.

Highlights in v2.4.0 include:

- [**Spice Cayenne by Default**](#spice-cayenne-by-default): automatic primary-key handling, persistent secondary indexes, and runtime-wide adaptive tuning.
- [**AI Decisions in SQL and HTTP**](#ai-decisions-in-sql-and-http): five SQL functions and an OpenAI-compatible `POST /v1/decisions` API.
- [**S3 Event-Driven Ingestion**](#s3-event-driven-ingestion): load new S3 objects when S3 event notifications arrive through SQS, with periodic backfill for missed events.
- [**Acceleration Snapshots**](#acceleration-snapshots) (Enterprise): read published snapshots without the source connector, with shared storage configuration and automatic retention.
- [**SQL Results-Cache Warmup**](#sql-results-cache-and-http-caching): record query shapes, then replay them after a restart so that the first queries use a warm cache.
- [**New Data Connectors and Formats**](#new-data-connectors-and-formats): query Hugging Face datasets, ORC files, and Iceberg tables without a catalog.

## What's New in v2.4.0

### Spice Cayenne by Default

[Spice Cayenne](https://spiceai.org/docs/components/data-accelerators/cayenne) now accelerates datasets and views that omit `acceleration.engine`, not in-memory arrow arrays. Storage still defaults to `mode: memory`. Set `mode: file` for persistent acceleration. Native Windows builds retain Arrow as their default.

#### Automatic ON CONFLICT handling for Primary Keys

A Cayenne dataset with a `primary_key` can now automatically handle `ON CONFLICT` resolution for all refresg paradigms.

| Dataset | Version kept for a repeated key |
| ------- | ------------------------------- |
| No `time_column` | The last arrival. |
| `time_column` with full or append refresh | The newest time. The last arrival wins a tie. A NULL time is oldest. |
| `refresh_mode: changes` | Each change applies in source order. |

```yaml
datasets:
  - from: s3://my-bucket/orders/
    name: orders
    time_column: updated_at
    params:
      file_format: parquet
    acceleration:
      enabled: true
      mode: file
      primary_key: id
```

Cayenne no longer uses `on_conflict` to select its conflict policy. For read-write datasets whose writes must stay in the acceleration, set `access: read_write` and `acceleration.write_mode: acceleration`. The source need not support writes. This setting cannot accompany a change-stream refresh (`refresh_mode: changes`, or a CDC source whose default refresh mode is `changes`).

An `UPDATE` that creates a primary-key collision fails before it changes rows. See the [migration guidance](#accelerator-selection-and-primary-key-policies).

#### Runtime-Wide Adaptive Tuning

Configure adaptive tuning for Cayenne datasets and catalogs at the `runtime` level. Adaptive tuning is in preview. 

```yaml
runtime:
  adaptive_tuning: enabled
  params:
    target_freshness: 30s

datasets:
  - from: postgres:public.orders
    name: orders
    acceleration:
      enabled: true
      mode: file
      refresh_mode: changes
      primary_key: id
```

Adaptive tuning accepts four targets and one pacing setting in `runtime.params`. Cayenne changes its settings in small steps to move each measured value toward its target:

- `target_replication_lag`: Desired maximum age of the newest applied source commit. Applies only to change-stream (`refresh_mode: changes`) datasets.
- `target_freshness`: Desired maximum delay from a source commit until its data becomes queryable. Applies only to change-stream datasets.
- `target_query_latency`: Desired P99 latency of the queries that read each Cayenne dataset.
- `target_qph`: Desired throughput, in queries per hour, of queries that read Cayenne datasets.
- `target_convergence_window`: Time budget for tuning to approach its targets. Default: `60s`.

Adaptive tuning defaults to `disabled`. Targets apply only when adaptive tuning is enabled. A `refresh_mode: full` dataset does not use adaptive tuning: each refresh replaces the whole table, so Cayenne turns off background compaction (`cayenne_compaction_background_interval_ms: 0`), and the tuner runs on that task. The runtime logs a warning for each such dataset. See [Cayenne Tuning Settings](#cayenne-tuning-settings).

#### Indexes, Initial Loads, and Compaction

- **Persistent secondary indexes**: File-mode Cayenne stores index runs with its acceleration. Writes maintain the indexes, and acceleration snapshots retain them. Indexes now accept floating-point columns. Dynamic join filters can probe secondary indexes.
- **Keyed initial loads**: Cayenne can build the primary-key filter during the first load within its memory budget. Otherwise, it retains the existing warmup path. Bulk loads avoid per-row routing and a subsequent whole-table fold.
- **Maintained aggregates**: Views share a compact index of per-key contributions. Rebuilds capture concurrent writes and apply them after the scan. A bounded query pool assigns 10% to aggregates without the former 512 MiB cap. An unbounded pool retains that cap.
- **Append-only compaction**: For unkeyed datasets without position deletes, Cayenne encodes merged files outside the write lock. Publication still takes the lock. Datasets with position deletes retain the full-rewrite path.
- **Configuration updates**: A restart applies changed write settings to an existing acceleration. Identity changes can rebuild eligible full-refresh accelerations from their source. See the [Cayenne documentation](https://spiceai.org/docs/components/data-accelerators/cayenne).

### AI Decisions in SQL and HTTP

Spice introduces introduces OpenAI compatible `POST /v1/decisions` support, TypeSafe decision model support, and 5 SQL decision functions. Any `model` LLM can also be used for AI decisions, via uncalibrated chat-model estimates.

Typesafe models are added to Spice as a model:
```yaml
models:
  - from: typesafe:jev
    name: support_model
    params:
      typesafe_api_key: ${secrets:TYPESAFE_API_KEY}
```

And can be used, as with all decision models, in SQL
| Function | Result |
| -------- | ------ |
| `ai_if(input, condition)` | `BOOLEAN`: true when the probability of yes exceeds 0.5. |
| `ai_probability(input, condition)` | `DOUBLE`: a probability from 0 to 1. |
| `ai_classify(input, labels)` | `VARCHAR`: one of the supplied labels. |
| `ai_score(input, instructions, levels)` | `DOUBLE`: a probability-weighted score. |
| `ai_decide(input, questions)` | `STRUCT`: answers, probabilities, and confidence. |

```sql
SELECT
    id,
    ai_classify(body, ['billing', 'technical', 'account'],
                model => 'support_model') AS team,
    ai_probability(body, 'The customer requests a refund',
                   model => 'support_model') AS refund_probability
FROM tickets
WHERE status = 'open';
```

### S3 Event-Driven Ingestion

With `refresh_mode: changes`, an [S3](https://spiceai.org/docs/components/data-connectors/s3) dataset loads new objects soon after they arrive. S3 sends an event notification to an SQS queue. Spice reads the notification from the queue, then the new object from S3. Set `refresh_mode: changes` and `s3_changes_queue_url` together. The queue must serve only this dataset, and `from` must be a prefix, not a single object or a glob:

```yaml
datasets:
  - from: s3://my-bucket/events/
    name: events
    params:
      file_format: parquet
      s3_region: us-east-1
      s3_changes_queue_url: ${secrets:events_queue_url}
    acceleration:
      enabled: true
      mode: file
      refresh_mode: changes
```

A periodic listing of the prefix (`s3_changes_backfill_interval`, default `1h`) loads objects whose notification was missed. Spice loads each object key one time. By default, rows from deleted objects stay in the acceleration (`s3_on_object_removed: ignore`).

### Acceleration Snapshots

Acceleration snapshots are a [Spice.ai Enterprise](https://docs.spice.ai/docs/enterprise) feature. OSS builds refuse snapshot datasets and do not publish snapshots.

A dataset can read published snapshots without the original source connector:

```yaml
datasets:
  - from: s3://my-bucket/spice/snapshots/
    name: orders
    params:
      file_format: snapshot
      s3_region: us-east-1
```


### One Location for Shared Runtime State

[`runtime.state`](https://spiceai.org/docs/reference/spicepod/runtime) provides a common location for object store state used across the runtime: cluster state and SQL results-cache warmup, and in Spice.ai Enterprise, shared HTTP rate control and acceleration snapshots:

```yaml
runtime:
  state:
    location: s3://my-bucket/spice/
    params:
      s3_region: us-east-1

datasets:
  - from: postgres:orders
    name: orders
    acceleration:
      enabled: true
      mode: file
      snapshots: enabled
```

Existing object store state locations (e.g. `runtime.scheduler.state_location`) are functional, but deprecated.

### SQL Results Cache and HTTP Caching

#### SQL Results-Cache Warmup

The [SQL results cache](https://spiceai.org/docs/features/caching) can record query shapes and store them. When Spice starts again, it replays the stored shapes after the first full or append refresh of each accelerated dataset:

```yaml
runtime:
  caching:
    sql_results:
      enabled: true
      warmup: on_first_refresh
```

Spice records the first 10 distinct shapes of cacheable, unauthenticated queries. Queries that differ only in equality-filter values share one shape. During replay, warmup reads up to 1,024 distinct values of each filtered column and reruns the shape with each value until the cache is full. Datasets do not report ready until warmup completes. Spice does not start when `warmup` is set together with `cache_key_type: sql`.

### New Data Connectors and Formats

#### Hugging Face Datasets

The [Hugging Face data connector](https://spiceai.org/docs/components/data-connectors) queries and accelerates Parquet, CSV, TSV, JSON, and ORC files from the Hub:

```yaml
datasets:
  - from: hf://datasets/stanfordnlp/imdb/plain_text/
    name: imdb
    acceleration:
      enabled: true
```

#### ORC and Object Metadata

Listing connectors now support `file_format: orc`. Enable metadata columns to query the location and modification time of each row's source object:

```yaml
datasets:
  - from: s3://my-bucket/events/
    name: events
    params:
      file_format: orc
      s3_region: us-east-1
    metadata:
      _location: enabled
      _last_modified: enabled
```

For example, query objects modified since October 1:

```sql
SELECT DISTINCT _location, _last_modified
FROM events
WHERE _last_modified >= TIMESTAMP '2026-10-01 00:00:00';
```

#### Iceberg Without a Catalog

[Iceberg](https://spiceai.org/docs/components/data-connectors/iceberg) datasets can read a table directly from its root directory on local or object storage:

```yaml
datasets:
  - from: iceberg:s3://my-bucket/warehouse/db/taxis
    name: taxis
    params:
      iceberg_s3_region: us-east-1
      iceberg_metadata_path: /metadata/00003-8f2c.metadata.json # Can also pin to an explicit metadata version. Read-only.
```


### Operations and Observability

The runtime can send structured logs through the existing OTLP exporter:

```yaml
runtime:
  telemetry:
    otel_exporter:
      endpoint: otel-collector:4317
      signals: [metrics, logs]
  query:
    log_errors: execution
```

Log records carry severity, typed attributes, and the query trace ID. The runtime batches delivery on a dedicated export runtime. `signals` defaults to `[metrics]`.

| `runtime.query.log_errors` | Behavior |
| -------------------------- | -------- |
| `none` (default) | Memory refusals at `WARN`, other query failures at `DEBUG`. |
| `execution` | Also logs execution failures at `WARN`. |
| `all` | Also logs syntax and planning failures at `INFO`. |

Failure records contain `error_code` and `datasets`. They do not contain SQL text. See [observability](https://spiceai.org/docs/features/observability).

Other changes:

- **Refresh scheduling**: Full and append refreshes now write on dedicated refresh threads by default. With `runtime.params.dedicated_thread_pool: disabled`, refresh writes run as before.
- **Open-file limits on Unix**: The runtime raises its soft open-file limit to the hard limit at startup. On macOS, `kern.maxfilesperproc` also bounds the result. If the hard limit remains too low, the Cayenne error names the effective limit and the remedy.

- **Shared-state metrics**: `state_store_request_duration_ms{feature, operation}`, `state_store_conflicts_total{feature}`, and `state_store_cleanup_deleted_total{feature}` report requests, conditional-write conflicts, and cleanup.
- **Snapshot-reader errors**: A reader that cannot load a newer snapshot increments `dataset_acceleration_refresh_errors{mode="snapshot", reason="snapshot_download_failed"}`. It keeps serving its loaded snapshot and tries again on the next poll.
- **Prometheus scrapes**: Derived summary families emit one `HELP` and `TYPE` block per family. Strict parsers no longer reject the scrape for repeated metadata.
- **Datadog dashboard**: New panels cover snapshot freshness, Cayenne segment caches, and pod health.

### Security Improvements

- **Flight sessions**: Authentication precedes session creation. Sessions remain bound to their creating principal. TLS handshakes have a 10-second deadline, and Flight SQL statement updates count against the Flight write limit.
- **HTTP paths**: The HTTP connector rejects `request_path` values that URL parsing would rewrite outside their allowed paths. This covers encoded dot segments and control-character rewrites.

## Breaking Changes

### Accelerator Selection and Primary-Key Policies

**Cayenne is the default accelerator on supported platforms.** Datasets and views without `acceleration.engine` switch from Arrow to Cayenne. Native Windows keeps Arrow. If datasets rely on another accelerator's behavior, review the [Cayenne migration guide](https://spiceai.org/docs/components/data-accelerators/cayenne/migration) before the upgrade.

**Other accelerators are deprecated for removal in v2.5.** This applies to Arrow, DuckDB, SQLite, Turso, and PostgreSQL acceleration, and to the DuckDB vector engine. They remain available in v2.4. A startup warning groups affected components by accelerator.

To retain Arrow temporarily in v2.4, name it explicitly:

```yaml
acceleration:
  enabled: true
  engine: arrow
```

Plan migration before v2.5. Do not delete acceleration-only data to change accelerators. Keep those datasets on v2.4 until a supported migration can preserve their data. The migration guide describes other limitations and vector-score changes.

**`on_conflict` is deprecated for removal in v3.0.** Cayenne accepts the field but no longer applies its policy. A primary key selects automatic version resolution. Before an upgrade, review `drop` policies and policies that reject conflicts. Other accelerators retain their existing policies in v2.4.

**`on_conflict` no longer routes writes to the acceleration, for all accelerators.** In v2.3, a read-write dataset that set `on_conflict` sent its writes to the acceleration, so its source did not need to accept writes. In v2.4, only `write_mode` selects where writes go. Such a dataset does not load if its source cannot accept writes. To keep writes in the acceleration, set `write_mode: acceleration`:

```yaml
datasets:
  - from: s3://my-bucket/orders/
    name: orders
    access: read_write
    params:
      file_format: parquet
    acceleration:
      enabled: true
      mode: file
      primary_key: id
      write_mode: acceleration
```

### SQL Results-Cache Freshness

Full and append refreshes, CDC batches, and retention passes no longer invalidate entries in the SQL results cache. Queries can return data from before the latest refresh until `item_ttl` expires. The `stale_while_revalidate_ttl` setting can extend this period. Review both settings before the upgrade. Reduce them if results must reflect refreshed data sooner.

### HTTP Rate-Control Wait Timeouts

If `rate_control_acquire_timeout` is unset, an HTTP request now waits up to the connector's `client_timeout` for rate-control capacity. Requests previously waited without a limit. Set `rate_control_acquire_timeout: 0` under the dataset's `params` to retain unbounded waits. Otherwise, choose a duration that matches the request budget, such as `30s`.

### Iceberg REST Compatibility

`GET /v1/namespaces/{namespace}/tables/{table}` now returns HTTP 400 with `BadRequestException` for accelerated datasets, views, and other unsupported datasets. The endpoint no longer synthesizes metadata for those datasets. For schema discovery, use SQL `DESCRIBE` or `information_schema.columns`. For queries, use `/v1/sql` or Arrow Flight SQL. Eligible unaccelerated Iceberg datasets expose their source metadata, and clients need their own storage credentials.

### Instance Identity and Cluster Upgrades

Instance identity resolves in this order: nonempty `SPICE_INSTANCE_ID`, `HOSTNAME`, `COMPUTERNAME`, then the host name. A scheduler's default changes from `host:port` to the host name. Executors also register under the instance identity.

If several schedulers or executors share a host, give each a distinct `SPICE_INSTANCE_ID`. Upgrade schedulers before executors. Older schedulers cannot fan out task-history requests to newer identity-based registrations. All cluster components must use compatible Ballista protocol versions.

PostgreSQL replication slots keep their names when a nonempty identity environment variable already selected the instance name. Without those variables, the host-name fallback creates a new slot. An empty `SPICE_INSTANCE_ID` also changes the previous slot name. After the new slot works, drop the unused old slot to stop its WAL retention:

```sql
SELECT pg_drop_replication_slot('<old slot name>');
```

### Shared State and Snapshot Migration

The top-level `snapshots` section and `runtime.scheduler.state_location` and `params` are deprecated. They continue to work, and when set they take priority over `runtime.state` for their feature. Prefer `runtime.state`, with per-dataset overrides (`acceleration.snapshots_location`, `acceleration.snapshots_params`) when necessary.

For upgrades from rc.1, move state from the shared root into these folders:

| State | Subdirectory |
| ----- | ------------ |
| Cluster scheduler | `cluster/` |
| Rate control | `rate-control/` |
| SQL results-cache warmup | `results-cache/` |

An explicit legacy scheduler location retains its earlier layout until migrated. In rc.1, Azure state ignored the URL path and used the container root. Move that state into the configured path and feature subdirectory.

The configured store must support writes and conditional writes. The runtime refuses newer state formats and stores that ignore write conditions. Check storage permissions before the upgrade.

Snapshots now expire automatically after 28 days, except for each dataset's current and newest snapshot. Rollback cannot select a pruned snapshot. Review external retention requirements before the upgrade.

Upgrade snapshot readers before, or alongside, their writers. Cayenne writes format 2 of the metastore slice when a snapshot contains partition children or pending write-back markers. Older readers reject that format. Other slices retain format 1.

Cayenne cannot publish acceleration snapshots for datasets with `cayenne_datalake_location`. Review snapshot settings for those datasets.

For a serving snapshot reader, `bootstrap_on_failure_behavior: retry` no longer retries a newer snapshot indefinitely inside one refresh. The reader reports the failure and retries at the next poll. Startup behavior does not change.

### Cayenne Tuning Settings

Replace retired per-dataset and per-catalog tuning settings with runtime settings:

| Previous setting | Replacement |
| ---------------- | ----------- |
| `cayenne_tuning: adaptive` | `runtime.adaptive_tuning: enabled` |
| `cayenne_tuning: auto` | `runtime.adaptive_tuning: disabled` |
| `cayenne_goal_replication_lag` | `runtime.params.target_replication_lag` |
| `cayenne_goal_freshness` | `runtime.params.target_freshness` |
| `cayenne_goal_query_latency` | `runtime.params.target_query_latency` |
| `cayenne_goal_convergence_window` | `runtime.params.target_convergence_window` |
| `cayenne_goal_qph` | `runtime.params.target_qph` |

The runtime no longer applies the old names. It warns with their replacements. Targets are runtime-wide. `runtime.adaptive_tuning` accepts only `enabled` or `disabled`. A Boolean such as `true` fails Spicepod loading.

## Upgrading

Review [Breaking Changes](#breaking-changes) before upgrading. Upgrade all distributed cluster components together, with schedulers before executors.

Upgrade snapshot readers before, or alongside, their writers so they can read the newer Cayenne metastore slice format.

Once the v2.4.0 release artifacts are available, use one of these methods:

**CLI**:

```console
spice upgrade v2.4.0
```

**Homebrew**:

```console
brew upgrade spiceai/spiceai/spice
```

Homebrew follows the version published in the tap.

**Docker**:

```console
docker pull spiceai/spiceai:2.4.0
```

See [Docker Hub](https://hub.docker.com/r/spiceai/spiceai/tags) for available tags.

**Helm**:

```console
helm repo update
helm upgrade spiceai spiceai/spiceai --version 2.4.0
```

**AWS Marketplace**:

Spice is available in the [AWS Marketplace](https://aws.amazon.com/marketplace/pp/prodview-jmf6jskjvnq7i). Marketplace availability follows its published versions.
