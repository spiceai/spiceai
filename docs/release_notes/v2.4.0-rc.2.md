# Spice v2.4.0-rc.2 (October 15, 2026)

Spice v2.4.0-rc.2 is the second release candidate of v2.4.0 for early testing and feedback. It introduces a new OpenAI-compatible `POST /v1/decisions` API backed by an OpenAI decision model, TypeSafe Jev, or any other LLM in the Spicepod that can answer decisions. Five new SQL functions bring the same AI classification, scoring, and decisions into SQL.

This release also adds Iceberg reads without a catalog and improves acceleration snapshots. Cayenne gains runtime-wide adaptive tuning and applies acceleration configuration changes on restart. The runtime can also store OpenTelemetry metrics as time series that SQL can query.

Highlights in this release:

- [**AI Decisions API and decisions in SQL**](#ai-decisions-api-and-decisions-in-sql): An OpenAI-compatible `/v1/decisions` API, plus five SQL functions for filtering, classifying, and scoring data with models.
- [**Iceberg without a catalog**](#iceberg-without-a-catalog): Read a table directly from its root directory or pin a metadata file to read a fixed version.
- [**OpenTelemetry metrics as time series**](#opentelemetry-metrics-as-time-series): One dataset stores every OTLP metric, and three SQL functions compute quantiles, increases, and rates.
- [**Shared runtime state**](#shared-runtime-state): Startup validation, conditional writes, one instance identity, and a common location for cluster state, rate control, cache warmup, and acceleration snapshots.
- [**SQL results cache**](#sql-results-cache): Cache entries expire by TTL and remain available across data refreshes.
- [**Cayenne acceleration**](#cayenne-acceleration): Improvements to primary-key loading, secondary indexes, and configuration updates.

These notes cover changes since [v2.4.0-rc.1](v2.4.0-rc.1.md). Review [Breaking Changes](#breaking-changes) before upgrading; upgrades from earlier versions also require the [rc.1 migration guidance](v2.4.0-rc.1.md#breaking-changes).

## What's New in v2.4.0-rc.2

### AI Decisions API and decisions in SQL

Spice now supports `POST /v1/decisions`, which is compatible with the [OpenAI Decisions API](https://developers.openai.com/api/docs/guides/decisions). A decision request asks typed questions about an input. Each answer comes back with its probabilities and a confidence.

Any model in the Spicepod can answer a decision request:

| Model                   | Example `from`                                     | Probabilities                    |
| ----------------------- | -------------------------------------------------- | -------------------------------- |
| OpenAI decision model   | `openai:gpt-6-luna`                                | The estimates of the model.      |
| TypeSafe decision model | `typesafe:jev`                                     | Calibrated by the model.         |
| Any other LLM           | `openai:gpt-4o-mini`, `anthropic:claude-haiku-4-5` | The estimates of the chat model. |

OpenAI decision models use the native OpenAI Decisions API. `gpt-6-luna` also supports chat and `/v1/nsql`. TypeSafe Jev returns calibrated probabilities and answers decisions only. Other LLMs answer through chat completions and return their own uncalibrated estimates.

```yaml
models:
  - from: openai:gpt-6-luna
    name: luna
    params:
      openai_api_key: ${secrets:OPENAI_API_KEY}
  - from: typesafe:jev
    name: jev
    params:
      typesafe_api_key: ${secrets:TYPESAFE_API_KEY}
```

Five new SQL functions make the same decisions available in queries:

| Function                                | Result                                                                   |
| --------------------------------------- | ------------------------------------------------------------------------ |
| `ai_if(input, condition)`               | `BOOLEAN`: true when the probability of "yes" exceeds 0.5.               |
| `ai_probability(input, condition)`      | `DOUBLE`: a probability from 0 to 1.                                     |
| `ai_classify(input, labels)`            | `VARCHAR`: one of the supplied labels.                                   |
| `ai_score(input, instructions, levels)` | `DOUBLE`: a probability-weighted score.                                  |
| `ai_decide(input, questions)`           | `STRUCT`: answers, probabilities, and confidence for a set of questions. |


```sql
SELECT
    id,
    ai_classify(body, ['billing', 'technical', 'account'], model => 'support_model' ) AS team,
    ai_probability(body, 'The customer is requesting a refund', model => 'support_model') AS refund_probability
FROM tickets
WHERE status = 'open';
```

See [AI functions](https://spiceai.org/docs/reference/sql/ai) for more examples.

### Iceberg Without a Catalog

Read an Iceberg table directly from object storage or the local filesystem, without configuring a catalog. Set `from` to the table root using `file://`, `s3://`, `s3a://`, `gs://`, or `gcs://`:

```yaml
datasets:
  - from: iceberg:s3://my-bucket/warehouse/db/taxis
    name: taxis
    params:
      iceberg_s3_region: us-east-1
```

Spice resolves the metadata file on each query and refresh. It supports `metadata/version-hint.text` as well as a fixed version (a path relative to the table root or a full URL):

```yaml
datasets:
  - from: iceberg:s3://my-bucket/warehouse/db/taxis
    name: taxis
    params:
      iceberg_s3_region: us-east-1
      iceberg_metadata_path: /metadata/00003-8f2c.metadata.json
```

Fixed tables are read-only. The earlier `metadata_path` parameter remains supported with a deprecation warning; see [Breaking Changes](#breaking-changes).

### OpenTelemetry Metrics as Time Series

The runtime can store every OTLP metric in one dataset with a fixed schema. Set `otlp_metrics: all` on a writable `sink:` dataset:

```yaml
datasets:
  - from: sink:otel_metrics
    name: otel_metrics
    access: read_write
    params:
      otlp_metrics: all
    time_column: time_unix_nano
    time_format: unix_nanos
    acceleration:
      enabled: true
      engine: cayenne
      mode: file
      refresh_mode: append
      primary_key: (time_unix_nano, series_hash)
```

The dataset stores gauges, sums, histograms, exponential histograms, and summaries. The `series_hash` column identifies the time series of each row. A new attribute key does not change the schema. The primary key `(time_unix_nano, series_hash)` drops the duplicate rows of a retried export. Per-metric `sink:` datasets continue to work.

The runtime also receives OTLP over HTTP at `POST /v1/metrics`. The endpoint accepts protobuf and JSON bodies, with optional gzip compression. It applies the same API key authentication, mTLS checks, and 128 MiB body limit as other HTTP writes.

Three new SQL aggregate functions query the stored metrics:

| Function                                                | Result                                                                                       |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `histogram_quantile(q, explicit_bounds, bucket_counts)` | The quantile `q` of the summed histogram buckets, with the same interpolation as Prometheus. |
| `increase(value, time)`                                 | The increase of a counter in the group. A decrease counts as a counter reset.                |
| `rate(value, time)`                                     | The increase per second between the first and the last sample.                               |

```sql
SELECT date_bin(INTERVAL '1 minute', to_timestamp_nanos(time_unix_nano)) AS t,
       histogram_quantile(0.99, explicit_bounds, bucket_counts) AS p99
FROM otel_metrics
WHERE metric_name = 'http.server.request.duration' AND temporality = 'delta'
GROUP BY 1;
```

Unlike PromQL, `increase` and `rate` do not extrapolate to the edges of the window. They use only the samples in the group.

### Shared Runtime State

`runtime.state` provides a shared, object-store location for cluster state, rate control, SQL results-cache warmup, and acceleration snapshots. Each feature uses its own subdirectory within the provided location.

Acceleration snapshots now default to the `snapshots/` subdirectory when `runtime.state` is configured.

```yaml
runtime:
  state:
    location: s3://my-bucket/spice/

datasets:
  - from: postgres:orders
    name: orders
    acceleration:
      enabled: true
      engine: cayenne
      mode: file
      snapshots: enabled
```

A dataset can override the snapshot location, its settings, and the bootstrap behavior on its own acceleration:

```yaml
datasets:
  - from: postgres:events
    name: events
    acceleration:
      snapshots: enabled
      snapshots_location: s3://archive-bucket/snapshots/
      snapshots_params:
        s3_region: eu-west-1
      snapshots_bootstrap_on_failure_behavior: fallback
```

Other changes to shared state:

- **Conditional writes:** Every write of shared state to object storage is now conditional. A writer that loses a race reads the current value again. Then it applies its change again or yields. It does not overwrite the update of the other writer.
- **Instance identity:** Every feature that uses shared state identifies an instance the same way. The runtime uses `SPICE_INSTANCE_ID`, then `HOSTNAME`, then `COMPUTERNAME`, then the host name.
- **Snapshot queues:** An SQS queue that covers the whole `runtime.state` prefix no longer causes an `ERROR` log for each scheduler heartbeat. The snapshot reader now deletes messages for the other state folders without a log.

The top-level `snapshots` section and the `runtime.scheduler` state settings are now deprecated. See [Breaking Changes](#breaking-changes) for the state-directory migration, the deprecations, and the instance identity.

### SQL Results Cache

The SQL results cache now expires entries by TTL, independent of acceleration refreshes, CDC batches, and retention passes no longer invalidate cached results.

Review `item_ttl` and `stale_while_revalidate_ttl` when upgrading: a successful refresh no longer makes cached results reflect the refreshed data immediately. See [Breaking Changes](#breaking-changes).

### Cayenne Acceleration

**Adaptive tuning is configured once for the runtime.** Enable it with `runtime.adaptive_tuning` and set targets under `runtime.params`:

```yaml
runtime:
  adaptive_tuning: enabled
  params:
    target_freshness: 30s
```

Supported targets are `target_replication_lag`, `target_freshness`, `target_query_latency`, `target_convergence_window`, and `target_qph`. Adaptive tuning defaults to `disabled`. See [Breaking Changes](#breaking-changes) and the `runtime` YAML [documentation](https://spiceai.org/docs/reference/spicepod/runtime).

Other Cayenne improvements include:

- **Primary-key loading:** Keyed tables build their primary-key filter during the initial load and bulk-load without per-row routing or a whole-table fold.
- **Position deletes:** `cayenne_deletion_mode: auto` can select position deletes for small primary-key tables on local storage on Linux systems with at least eight physical cores.
- **Secondary indexes:** Index runs are persisted, indexes remain complete across acceleration snapshots, and CDC maintains indexes for each operation type. Hash joins read each file once when narrowing a scan through an index.
- **Partition handling:** Cayenne rejects stored data with an incompatible `partition_by`, protects keyed appends to partitioned tables during publication, and prepares every partition after a refresh.
- **Storage and query correctness:** Cayenne reclaims snapshot directories superseded by a reload, corrects pruning for NaN values, and fixes deletion-index bounds and reload fencing.
- **Snapshot storage growth:** A writer with `snapshots_trigger: refresh_complete` kept one more copy of the table for each refresh. Each snapshot held file deletions, so Cayenne skipped each cleanup pass. Cayenne now runs the cleanup when a snapshot releases its hold. In a 10-minute test with a refresh every 60 seconds, each dataset kept 1 snapshot directory instead of 10.
- **Write strategies:** Datasets with `cayenne_compression_strategy: zstd`, or with `cayenne_delta_encoding` set to `4`, `5`, or `6`, failed every write. The error was `Serialized array ID fastlanes.delta not permitted by ctx`. These strategies included an encoding that no enabled Vortex edition permits. Cayenne now removes such encodings from every strategy that it builds.
- **Configuration changes on restart:** A change to write settings only, such as `cayenne_sort_columns` or `cayenne_compression_strategy`, applies to the existing acceleration. A change to `primary_key` or `partition_by` rebuilds the acceleration from the source only under specific conditions. See [Cayenne Configuration Updates](#cayenne-configuration-updates).

## Fixes and Improvements

### AI APIs and Models

- **Responses API:** `/v1/responses` executes Spice tools and honors `tool_recursion_limit` when streaming. It returns Spice tool calls as `mcp_call` items in `output`, allowing clients that manage their own conversation history to replay them.
- **Model controls:** `/v1/nsql` accepts `reasoning_effort`, and `rerank()` uses evaluation models with a strategy selected for each query.
- **Anthropic:** Streaming handles responses that begin with a thinking block, empty text blocks are dropped, and `anthropic_workspace_id` is available as a model parameter.
- **OpenAI:** Models with an unknown service tier can load and serve requests.
- **Luna:** `gpt-6-luna` and its snapshots support chat, `/v1/nsql`, and native decisions.

### Acceleration

- **Caching point lookups:** Lookups on a `refresh_mode: caching` dataset failed with HTTP 400. This occurred when Cayenne accelerated the dataset, the primary key covered the request columns, and the table held two protected snapshots. The point-lookup plan did not combine the partitions of the Cayenne scan. Lookups now return the cached row or fetch it from the source.

### Distributed Cluster

- **Slot lending for HTTP sources:** A distributed task that waits for a slow HTTP response now lends its executor task slot to other queries. The task takes a slot back when the response arrives.
- **Task history:** In a cluster with more than one scheduler, `runtime.task_history` failed on some schedulers with `table 'spice.runtime.local_task_history' not found`. On other schedulers, the result did not include the rows of peer schedulers. The cause was that the query planner sent the scan of a node-local table to an executor. Each scheduler now reads its own task history, and the result includes the rows of each peer.

### Connectors

- **MySQL timestamps:** Timestamp literals in queries that the runtime sends to MySQL now keep their fractional seconds.

## Breaking Changes

### Shared State Directory Layout and Startup Checks

State written at the `runtime.state` root by rc.1 is no longer read from that location. Move existing state objects into the appropriate subdirectories before upgrading to retain them:

| State                    | Subdirectory     |
| ------------------------ | ---------------- |
| Cluster scheduler        | `cluster/`       |
| Rate control             | `rate-control/`  |
| SQL results-cache warmup | `results-cache/` |

Azure locations (`abfs://` and `abfss://`) need one more step. In rc.1, the runtime ignored the path in an Azure URL and wrote state at the container root. For example, with `abfs://container/spice/`, rc.1 wrote `cluster.json` at the container root. This release writes `spice/cluster/cluster.json`. Move Azure state from the container root into the configured path and then into the feature subdirectory.

An explicit `runtime.scheduler.state_location` retains its earlier layout, but that setting is now deprecated. Without migration, Spice starts without the state previously stored at the shared root.

The configured store must accept writes and conditional writes. Spice does not become ready until startup validation succeeds and refuses stores with a newer state format. Check storage permissions and compatibility before upgrading.

### Deprecated Snapshot and Scheduler State Settings

The top-level `snapshots` section is deprecated. The `runtime.scheduler.state_location` and `runtime.scheduler.params` settings are also deprecated. Use `runtime.state` for both. To use a different snapshot location for a dataset, set `snapshots_location` and `snapshots_params` on its acceleration.

Before:

```yaml
snapshots:
  location: s3://my-bucket/spice/snapshots/
  bootstrap_on_failure_behavior: fallback
```

After:

```yaml
runtime:
  state:
    location: s3://my-bucket/spice/

datasets:
  - from: postgres:orders
    name: orders
    acceleration:
      snapshots: enabled
      snapshots_bootstrap_on_failure_behavior: fallback
```

The deprecated settings continue to work. The runtime logs one warning at startup for each of them. The warning shows the configuration that keeps the existing objects at their current location.

### Instance Identity

Every feature that coordinates through shared state now uses one instance identity. The runtime takes it from `SPICE_INSTANCE_ID`, then `HOSTNAME`, then `COMPUTERNAME`, then the host name. The default identity of a scheduler changed from `host:port` to the host name. Executors now register under their identity.

- Set a different `SPICE_INSTANCE_ID` for each scheduler or executor that runs on the same host.
- Upgrade schedulers before executors. While older schedulers run, their `runtime.task_history` queries to newer schedulers fail.
- PostgreSQL replication slot names do not change when `SPICE_INSTANCE_ID`, `HOSTNAME`, or `COMPUTERNAME` is set. An instance without these variables, or with an empty `SPICE_INSTANCE_ID`, creates a new slot. The old slot keeps WAL on the source. Drop it with `SELECT pg_drop_replication_slot('<old slot name>')`.

### SQL Results Cache Freshness

A refresh no longer invalidates SQL results-cache entries. Queries can return data from before the latest refresh until `item_ttl` expires, plus `stale_while_revalidate_ttl` when configured. Reduce `item_ttl` if results need to follow source refreshes more closely.

### Cayenne Tuning Configuration

Replace the Cayenne tuning parameters with runtime settings that apply across datasets and catalogs:

| Previous parameter                | Replacement                                |
| --------------------------------- | ------------------------------------------ |
| `cayenne_tuning: adaptive`        | `runtime.adaptive_tuning: enabled`         |
| `cayenne_tuning: auto`            | `runtime.adaptive_tuning: disabled`        |
| `cayenne_goal_replication_lag`    | `runtime.params.target_replication_lag`    |
| `cayenne_goal_freshness`          | `runtime.params.target_freshness`          |
| `cayenne_goal_query_latency`      | `runtime.params.target_query_latency`      |
| `cayenne_goal_convergence_window` | `runtime.params.target_convergence_window` |
| `cayenne_goal_qph`                | `runtime.params.target_qph`                |

`runtime.adaptive_tuning` accepts only `enabled` or `disabled`. Other values, including `true`, fail the Spicepod load.

### Pinned Iceberg Tables

Replace the deprecated `metadata_path` parameter with `iceberg_metadata_path`. The two settings resolve paths differently. `metadata_path` uses its value as given. `iceberg_metadata_path` resolves a value without a URL scheme relative to the table root in `from`. Convert an absolute local path to a full `file://` URL or to a path relative to the table root.

Datasets pinned to a `.json` metadata file are read-only and fail to load with `access: read_write`. Remove that setting from pinned datasets before upgrading.

### Cayenne Configuration Updates

A restart now applies changed settings to an existing Cayenne acceleration. The result depends on the setting and the dataset:

- **Write settings only:** A change to only `cayenne_sort_columns`, `cayenne_cluster_by`, `cayenne_compression_strategy`, `cayenne_delta_encoding`, or `cayenne_shard_key_columns` applies to the existing acceleration. Stored rows keep their layout until a refresh or compaction rewrites them.
- **Identity settings:** A change to `primary_key`, `partition_by`, `cayenne_pk_conflict_detection` from `none` to `auto`, or the data location rebuilds the acceleration from the source. The runtime rebuilds only a dataset with `refresh_mode: full`, `mode: file` or `file_update`, and `write_mode: write_through`. The source must not be `sink:`, and must be readable with the schema of the dataset.
- **All other datasets:** The acceleration keeps all of its stored settings. This includes write settings that changed in the same restart. The runtime logs a warning that names the change and the fix.

While the runtime cannot read the source, a dataset that qualifies for a rebuild keeps its existing acceleration. A `partition_by` change or a conflict-detection change cannot use the stored rows, so it fails the dataset instead. Revert the setting, or restart when the source is readable.

A restart alone does not migrate a dataset that does not meet these conditions. Read the startup warning for the dataset before you delete stored data. Allow time for a rebuild when the conditions apply.

## Upgrading

Once release artifacts are available, select v2.4.0-rc.2 explicitly with the CLI, Docker tag, or Helm chart version.

### CLI

```console
spice upgrade v2.4.0-rc.2
```

### Docker

```console
docker pull spiceai/spiceai:2.4.0-rc.2
```

See [Docker Hub](https://hub.docker.com/r/spiceai/spiceai/tags) for available tags.

### Helm

```console
helm repo update
helm upgrade spiceai spiceai/spiceai --version 2.4.0-rc.2
```

### Homebrew and AWS Marketplace

Homebrew and AWS Marketplace follow their published versions. To select this release candidate, use an explicit version through the CLI or Docker.

```console
brew upgrade spiceai/spiceai/spice
```

Spice is also available in the [AWS Marketplace](https://aws.amazon.com/marketplace/pp/prodview-jmf6jskjvnq7i).
