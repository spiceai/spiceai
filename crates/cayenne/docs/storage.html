Metadata & data reference

What Cayenne stores, and where

Cayenne splits storage across a transactional metastore (SQLite / Turso), an immutable Vortex data lake, and an LSM level-0 tier. This is the authoritative map of every persisted table, file, and convention.

Source of truth

The DDL in crates/cayenne/src/metastore/sqlite.rs (mirrored in turso.rs) and the column lists in metastore::EXPECTED_TABLES. validate_existing_schema checks column names and ordering at startup — types aren't compared, since SQLite/libSQL type affinity makes exact matching unreliable. § 03 — Data lake

On-disk data layout

Vortex data files and Arrow-IPC deletion files live under the data root, grouped by table_id then snapshot directory:

The three snapshot kinds

A <snapshot_id> directory is a UUIDv7-named set of immutable Vortex files (and their deletion vectors). Three kinds coexist under one table, and they differ entirely in visibility and which deletions apply at scan time — not in their on-disk shape:

KindVisible to reads?Deletion filter at scanLifetime · created by
Currentyes — the base; cayenne_table.current_snapshot_idfull — every deletion appliesexactly one at a time; replaced by an atomic pointer flip. Genesis + compaction output
Stagingno — pre-visibilityn/atransient; written in Stage A of every burst under _wal.json. Stage B moves/publishes it; the WAL self-heals on crash
Protectedyes — unioned with currentpartial — only delete_seq > thresholdretained; they accumulate and are folded by maintenance compaction. Created by an on-conflict upsert / pending-PK-delete publish (key-delete path)

The why for protected snapshots: a publish stages freshly-inserted rows at sequence numbers above the deletions already baked into the current snapshot. Those older deletions provably cannot apply to the new rows, so the writer skips re-resolving the entire deletion set against them — it publishes the new data as a protected snapshot with a threshold = the snapshot's own allocated sequence (persisted in cayenne_snapshot_sequence, cached as protected_snapshots: snapshot_id → threshold). At scan time the read applies the full deletion filter to current and a partial one (delete_seq > threshold) to each protected snapshot, then unions them. They are never silently cleared — each holds valid data under its own filter; compact_protected_snapshots_subset (count/age-triggered) folds the older prefix into one self-contained merged snapshot, keeping the newest K unbaked and seq-prefix-baking delete_seq ≤ T.

Layout by workload shape

The same primitives produce visibly different trees depending on whether the workload deletes. Three representative shapes:

Vortex data files

Immutable once written. Target size cayenne_target_file_size_mb (default 256 MB); btrblocks (default) or zstd compression; optional sort columns. A "file" (DataFile) is a Vortex ListingTable rooted at a unique directory, not necessarily one object. Footer stats are cached in cayenne_snapshot_file_statistics.

Deletion files — the schema is the discriminator

ModeArrow schemaWhen
Position-basedrow_id: UInt64, deleted_at: Int64 (µs)PK-less tables (always), or any table in deletion_mode: position
Key-basedrow_key: Binary, deleted_at: Int64 (µs)PK tables in deletion_mode: key (auto ⇒ key for changes-mode PK tables)

Crash-safety & portability files

Staging WAL (_wal.json) — makes a staged file list crash-safe via tmp + fsync + rename; unreconciled markers self-heal on the next open. Partitioned WAL — anchors a cross-partition atomic commit. Snapshot slice (metadata/<dataset>.slice.json) — a versioned (format_version: 1) per-dataset metastore export, path-re-anchored on import for portability across nodes. The raw cayenne.db/-wal/-shm are excluded from the snapshot tar.

§ 04 — In-memory

In-memory state — an ontology

CayenneTableProvider carries ~57 fields of in-memory state (provider/table.rs:1894). They are not all data and not all ephemeral. The organizing question is durability class — what happens on a crash.

ClassMeaningOn crash
Derived cachefast-read projection of a durable source, rebuilt on openno loss — reloaded from metastore / files
EphemeralRAM-only payload, no durable copydiscarded, then re-streamed exactly-once from the source slot
Coordinationlocks, fences, atomics, flags — no payloadreconstructed empty
Accountingmemory-pool reservationsirrelevant
Are protected snapshots in memory?

Only as a derived cache. protected_snapshots: Arc<ArcSwap<HashMap<String,i64>>> (table.rs:2012) maps snapshot_id → minimum_sequence for wait-free read routing — but it is not the source of truth. load_protected_snapshots (table.rs:17511) rebuilds it from the durable cayenne_snapshot_sequence table on every open and restart, and writes go to both set_snapshot_sequence (persist) and protected_snapshots.rcu(…) (refresh). The snapshot data lives in on-disk per-snapshot directories. Protected snapshots are durable; the ArcSwap is just the index in front of them — and the same is true of nearly every "cache" below.

Concurrency vocabulary

ArcSwap<T> — wait-free RCU (readers load() an immutable Arc, never block; writers swap a new T in).  im::HashMap — persistent HAMT, O(1) clone on append.  tokio::{Mutex,RwLock} — async (held across I/O).  parking_lot::Mutex — short sync sections.  Atomic*/OnceLock — counters/flags / one-time task init.

E · CDC mem-tier — ephemeral (RAM-only; re-streamed exactly-once)

The only data-bearing state with no durable copy. mem_tier: Arc<ArcSwap<MemTier>> (provider/mem_tier.rs), empty in file mode. On crash it's discarded; the source slot holds the last-checkpointed LSN, the source re-streams past it, and the PK-idempotent apply reconciles exactly-once. The SlotAdvancer advances the slot only after a checkpoint is durable.

§ 05 — Conventions

Identifiers, sequences & validation

  • Identifiers — UUIDv7 text everywhere except cayenne_insert_record.table_id, stored as the 16 raw UUID bytes (a pure re-encoding to shrink the hot upsert table's clustered key).
  • Sequence numbers — monotonic, reserved from the metastore (reserve_sequence_numbers batches reservations). Every insert/delete/re-insertion carries one; the scan resolves "deleted, and re-inserted after that?" from them.
  • Visibility — the authoritative state is cayenne_table.current_snapshot_id; visible by an atomic pointer flip under the listing fence, never in-place mutation.
  • Schema validation — validate_existing_schema compares column names + ordering only; a mismatch returns CatalogError::SchemaMismatch with a "clear your acceleration data" message.
  • Backends — SQLite uses BEGIN IMMEDIATE; Turso uses BEGIN CONCURRENT (MVCC). DDL is identical except WITHOUT ROWID (SQLite-only).

The DDL source (metastore/sqlite.rs) is authoritative; treat this as a quick reference. See the README for how these structures are used, and the architecture tour for the mechanisms.
