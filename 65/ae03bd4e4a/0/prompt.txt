# Plan: Add Partitioning Support to Arrow In-Memory Acceleration

## Context
The Arrow acceleration engine is the default in-memory accelerator in Spice. Currently it rejects any `partition_by` configuration with an error. DuckDB and Cayenne already support partitioning via a separate `PartitionCreator` implementation that wraps the engine's `TableProvider` in a `PartitionTableProvider`. We want the same capability for Arrow (in-memory).

The key difference vs DuckDB: Arrow is purely in-memory, so there are no files to persist or infer from disk. `infer_existing_partitions()` always returns `vec![]`.

## Step-by-Step Changes

### 1. `crates/runtime-acceleration/src/engine.rs`

Add `PartitionedArrow` to the `Engine` enum:
```rust
pub enum Engine {
    #[default]
    Arrow,
    PartitionedArrow,  // new
    DuckDB,
    ...
}
```

Update `to_unpartitioned()`:
```rust
Engine::PartitionedArrow => Engine::Arrow,
Engine::PartitionedDuckDB | Engine::TableModePartitionedDuckDB => Engine::DuckDB,
```

Update `Display` (show "arrow" for `PartitionedArrow`):
```rust
Engine::Arrow | Engine::PartitionedArrow => write!(f, "arrow"),
```

### 2. `crates/runtime/src/component/dataset/acceleration.rs`

Inside the `Engine::try_from(engine_str)` match block (around line 403), add a new arm analogous to the DuckDB one:
```rust
Engine::Arrow if !acceleration.partition_by.is_empty() => Engine::PartitionedArrow,
```

### 3. `crates/runtime/src/dataaccelerator/mod.rs`

Add:
```rust
pub mod partitioned_arrow;
```

### 4. `crates/runtime/src/dataaccelerator/arrow.rs`

Remove the guard that rejects `partition_by` (lines 77–82). The routing in step 2 ensures `ArrowAccelerator::create_external_table` is only called when `partition_by` is empty.

### 5. `crates/runtime/src/dataaccelerator/partitioned_arrow.rs` (new)

Implement two structs:

**`ArrowPartitionCreator`** — implements `PartitionCreator`:
- Stores: `cmd: CreateExternalTable`, `partition_by: Vec<PartitionedBy>`, `schema: SchemaRef`
- `create_partition(values)`: calls `ArrowFactory::create()` (via `TableProviderFactory::create`) with the stored `cmd` to create a new in-memory MemTable, wraps it in a `Partition { partition_values: values, table_provider }`
- `infer_existing_partitions()`: returns `Ok(vec![])` — Arrow is in-memory, no prior state to recover
- `supports_filters_pushdown(filters)`: returns `Inexact` for all filters (same as Arrow MemTable default)

**`PartitionedArrowAccelerator`** — implements `DataAccelerator`:
- `name()` → `"partitioned_arrow"`
- `prefix()` → `"arrow"` (same as ArrowAccelerator)
- `parameters()` → reuse PARAMETERS from `arrow.rs` (move to a shared const or duplicate)
- `create_external_table(cmd, source, partition_by)`:
  1. `ensure!(!partition_by.is_empty(), ...)`
  2. Build `schema` from `cmd.schema.as_arrow()`
  3. Create `Arc<ArrowPartitionCreator>`
  4. Wrap in `PartitionTableProvider::new(creator, partition_by, schema).await?`
  5. Return as `Arc<dyn TableProvider>`
- Register: `register_data_accelerator!(Engine::PartitionedArrow, PartitionedArrowAccelerator);`
